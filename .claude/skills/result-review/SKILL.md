# 結果檢討

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「看到什麼現象 → 代表什麼問題 → 下一次怎麼改」，讓 AI 像店長一樣檢討。
> 每個現象都要把「實際觀察（數字來自試算結果）」和「推測（尚未證實）」分開寫。

## 什麼時候用

每跑完一次 `npm run simulate`，要決定下一版策略怎麼改時。

## 試算結果裡有哪些線索

試算工具每天會印出：客人數、收入、備貨、宣傳、報廢（清潔費）、淨利、任務、星等、資金，以及「沒買到的客人」：

| 線索 | 意思 |
|---|---|
| 賣完買不到 | 有人想買，但貨不夠 |
| 嫌太貴 | 價格超過客人剩下的預算 |
| 想吃的沒上架 | 客人想吃的菜今天沒賣 |
| 因為討厭的菜不進門 | 上架了某位客人討厭的菜 |

## 對症下藥表

| 看到的現象 | 代表的問題 | 下一次怎麼改 |
|---|---|---|
| 賣完買不到很多 | 備貨太少 | 那樣菜多備一些（注意合計不能超過 80 份） |
| 報廢 15 份以上 | ★ 觀察（v1）：第 3 天報廢 16 份、清潔費 83 元；五天總報廢 62 份，其中玉米鍋貼 32 份（第 1、3 天各報廢 10 份，賣出 0 份）、韭菜鍋貼 23 份。推測（未證實）：這兩樣的備貨高於實際需求；玉米賣不出去的原因可能是需求低或價格高，目前無法區分。 | ★ 減少報廢最多那樣菜的備貨，以 `reorder-check` 的建議值為準。一次最多改 3 處，先調整玉米與韭菜的備貨，不同時改價格。 |
| 嫌太貴很多 | ★ 觀察（v1）：第 1～5 天「嫌太貴」離開的人數分別為 8、7、5、6、8 人。試算結果沒有分菜列出。推測（未證實）：預算較低的客人買不起定價 70～80 元的菜，但無法確定是哪一樣菜造成的。 | ★ 只針對有證據的菜降價，而且要在可定價範圍內；先確認是哪一樣菜造成的，再調整，不同時改多樣的價格。 |
| 想吃的沒上架很多 | ★ 觀察（v1）：第 2 天「想吃的沒上架」11 人，其他天為 0。推測（未證實）：這些客人想吃的菜（例如豆漿、酸辣湯）不在 v1 的四樣上架內。 | ★ 上架上限是 4 樣，不能加到 5 樣。考慮把一個上架位換成客人想吃的菜，一次只換一處，再比較結果。 |
| 因為討厭的菜不進門 | ★ 觀察（v1）：第 1～5 天分別有 6、5、5、5、6 人因討厭的菜不進門。推測（未證實）：上架的菜剛好是部分客人討厭的菜；本次沒有對照客人包的討厭清單，無法確定是哪一樣。 | ★ 對照客人包的討厭清單。若某樣菜造成大量不進門，考慮不上架它，但要先確認它的需求與利潤。 |
| 星等往下掉 | ★ 觀察（v1）：第 3 天星等 2.5 → 1.5（進店 32 人：滿意 15、普通 4、不滿 13；招牌鍋貼缺貨 12 人）；第 2 天 3.5 → 2.5（進店 36 人：滿意 18、不滿 18）。推測（未證實）：缺貨與太貴造成不滿增加。 | ★ 增加缺貨那樣菜的備貨（例如招牌鍋貼），同時減少報廢多的菜；不要用改價格來處理星等問題。 |
| ★ 我自己發現的現象：宣傳後增加來客，但淨利未改善 | ★ 觀察：v1 沒有宣傳，這個現象在 v1 中沒有出現，無法用 v1 判斷。推測（未證實）：宣傳費增加的來客，帶來的收入不足以抵銷宣傳費與多出的備貨或清潔費；也可能新增的客人買到的是低毛利的菜。 | ★ 先核對，再調整：同一策略只加宣傳（0 → 200 元），比較來客數（customers）、收入（revenue）、成本（stockCost ＋ promoCost ＋ wasteFee）。淨利變化 ＝ 收入變化 − 備貨變化 − 宣傳變化 − 清潔費變化。若淨利沒有改善，先調整備貨或價格，不要直接加更多宣傳。 |

## 步驟

1. 讀試算結果，逐天找出上表的現象
2. 每一個現象，照對症下藥表提出一個修改
3. **一次最多改 3 個地方**，這樣才知道是哪個修改有效
4. 把修改後的策略存成新的檔案（例如 `plans/v2.json`），不要覆蓋舊的，方便比較

## 回報格式

```text
這一版的結果：最終資金 …、星等 …、報廢 …
發現的問題：
1. 第 N 天：（現象）→（問題）
修改：
1. …
下一版檔名：
```

## 不准做的事

- 不准修改遊戲檔案（`src/` 底下的任何檔案、客人包）
- 只能新增或修改 `web-lab/plans/` 裡的策略檔
- 不准把推測當成觀察結果寫入回報
