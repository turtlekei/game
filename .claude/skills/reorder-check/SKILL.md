# 補貨檢查

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「數字一定要從盤點資料抄，不能自己編」，而且每個數字都要能驗算。

## 什麼時候用

- 跑完 `npm run simulate`，要決定下一版策略每樣菜備幾份時
- 在瀏覽器玩完一天，想看「倉庫盤點」頁的結果該怎麼調整時

## 資料從哪裡來

在 `web-lab` 資料夾執行：

```text
npm run simulate -- plans/策略檔.json --json
```

每一天的 `inventory` 欄位，是那天每樣上架的菜的盤點：

| 欄位 | 意思 | 怎麼驗算 |
|---|---|---|
| `name` | 菜名 | — |
| `stocked` | 早上備了幾份 | 策略檔裡的 `qty` |
| `sold` | 賣出幾份 | 打烊報表 |
| `waste` | 報廢幾份 | 備貨 − 賣出 |
| `missed` | 賣完之後，還有幾位客人想買卻沒買到 | 客人卡片上「賣完了」的數量 |
| `status` | `ok` 正常、`out` 缺貨、`over` 報廢過多 | 規則書「倉庫盤點」 |
| `suggest` | 明天建議備幾份 | 賣出 ＋ 沒買到 |

## 步驟

1. 執行上面的指令，讀每一天的 `inventory`
2. 先驗算：逐筆檢查 `waste` 是否等於 `stocked − sold`。對不上的那一筆停止分析，指出天數與菜名；其他筆照常分析（見下方 ★「資料缺漏或互相矛盾」）
3. 挑出 `status` 不是 `ok` 的菜
4. ★ 建議備貨量：直接採用 `suggest`（賣出 ＋ 沒買到），不自行加緩衝量。客人會比較多的日子（事件倍率較高）也不自動加量，這類想法放到回報的「其他建議」給你審核。
5. ★ 同一樣菜連續兩天以上都是 `out` 或 `over`：提醒「這是持續現象」，並列出每一天的 `sold`、`waste`、`missed`、`status`。只有一天時，不說是趨勢，也不推測多天的走向。
6. 用下面的回報格式回報

## 回報格式

```text
策略檔：
驗算結果：通過 / 第 N 天的 ○○ 對不上（寫出哪個數字）
第 N 天：
  缺貨：菜名 備 … 賣 … 沒買到 … → 建議 …
  報廢過多：菜名 備 … 賣 … 報廢 … → 建議 …
★ 持續現象（連續兩天以上）：菜名 第 N～M 天，各天的 賣 … 報廢 … 沒買到 … 狀態 …
★ 相隔兩天賣出差異警告（比較第 N 天與第 N+2 天的 sold；絕對差 ≥ 5 份，且差異 ≥ 50%，以較小的那天為基準；基準為 0 時只看絕對差 ≥ 5 份）：
★ 其他建議（給你審核，不直接採用）：
下一版每天建議的備貨量：
```

## 寫完檢查

- [ ] 每一個數字都能在盤點資料裡找到
- [ ] ★ 每一條停止、警告、持續現象，都寫出天、菜名、欄位與數字；有缺漏或矛盾的那一筆，沒有給備貨建議

## 不准做的事

- 不准修改任何檔案（這個 Skill 只讀不寫，要改策略交給 result-review）
- 不准自己編數字，或用「大概」、「差不多」帶過
- ★ 資料缺漏或互相矛盾時，停止該筆的備貨建議，並指出哪一天、哪樣菜、哪個欄位有問題。矛盾的例子：`waste` ≠ `stocked − sold`、`sold` > `stocked`、`missed` > 0 但 `status` 不是 `out`、欄位缺漏或是負數。
- ★ 只有一天的資料時，不推測多天趨勢。
